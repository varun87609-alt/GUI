# OpenFOAM AutoMesh - Security Specification and Hardening Guide

## 1. Threat Model & Trust Boundaries

The application processes user-supplied 3D CAD files (`.stl`) and generates executable simulation inputs for OpenFOAM within an automated execution pipeline.

### Untrusted Inputs:
1. **Uploaded Geometry Files (`.stl`)**: May contain oversized buffers, malformed coordinate data, non-manifold topology, or crafted binary headers.
2. **Meshing Configuration Parameters**: Numbers, names, and multipliers supplied via the web form or API.
3. **Client Filenames**: Headers such as `Content-Disposition` containing potential path traversal characters (`../`, `..\`, null bytes).

### Trust Boundaries:
- **Client (Browser) <--> Backend API (FastAPI)**: Untrusted boundary. All data strictly validated via Pydantic schemas.
- **Backend API <--> Host Filesystem**: Semi-trusted boundary. Server assigns unique UUIDs for paths; user-supplied paths are rejected.
- **Backend API <--> Docker Daemon**: Trusted boundary via local named pipe / daemon. Containers are strictly isolated from the host.
- **Docker Container Sandbox <--> Host/Network**: Isolated sandbox. The container has no network access and cannot escape its mounted per-job directory.

## 2. Security Controls Implemented

### A. Upload & Filesystem Protection
- **Path Traversal Immunity**: Client filenames are stripped to their base name (`os.path.basename`) and stored strictly under server-generated UUID4 directories:
  ```python
  upload_id = str(uuid.uuid4())
  upload_dir = settings.uploads_path / upload_id
  target_path = upload_dir / "geometry.stl"
  ```
- **Stream-Enforced Size Limits**: Files are streamed to disk in 1 MB chunks while accumulating a byte counter. If the size exceeds 100 MB (`MAX_UPLOAD_SIZE_BYTES`), writing immediately halts, the partial file is removed, and `HTTP 413` is returned.
- **Binary/ASCII Geometry Validation**: The backend parses vertex arrays, checks that all coordinates are finite numbers (rejecting `NaN` and `Inf`), and validates facet normal integrity.
- **Cleanup of Partial/Failed Uploads**: If parsing fails or the request is aborted, uploaded files are promptly unlinked.

### B. Docker Isolation & Container Sandboxing
- **No Docker Socket Mounting**: The host Docker socket is never mounted into any container.
- **Complete Network Isolation**: Containers run with `network_mode: none`. OpenFOAM processes have zero network connectivity, eliminating potential data exfiltration or reverse-shell capabilities.
- **No-New-Privileges**: Containers are launched with `security_opt: ["no-new-privileges:true"]`, preventing privilege escalation via setuid/setgid binaries.
- **Strict Resource Constraints**:
  - `mem_limit: 4g` (prevents memory exhaustion from runaway refinement).
  - `nano_cpus: 2000000000` (caps CPU usage to 2 cores).
  - Concurrency limited to 2 simultaneous jobs via `JobQueueManager`.
- **Narrow Working Directory Mounting**: Only the isolated job directory (`workspace_jobs/jobs/<job_id>`) is mounted to `/workspace`. The host filesystem is not accessible.
- **Controlled Entrypoint**: The container entrypoint is strictly overridden to `/bin/bash` with an internal script generated by the backend. No user-supplied shell scripts are ever executed.

### C. Web Application & API Defenses
- **CORS Allowlist**: Cross-Origin Resource Sharing is restricted to configured origins (`ALLOWED_ORIGINS`).
- **Security Headers**: Every HTTP response includes:
  - `X-Content-Type-Options: nosniff`
  - `X-Frame-Options: DENY`
  - `X-XSS-Protection: 1; mode=block`
  - `Referrer-Policy: strict-origin-when-cross-origin`
- **Safe Log Rendering**: Real-time terminal logs are rendered strictly as text nodes in React, preventing HTML/script injection via crafted log outputs.
- **Information Leakage Prevention**: In non-debug mode, unhandled internal exceptions return generic JSON error messages rather than leaking Python tracebacks, Docker paths, or environment variables.

## 3. Residual Risks & Deployment Recommendations

1. **Local Single-User vs Multi-User**: The current database architecture is optimized for a single-user workstation or trusted lab environment. In a multi-tenant public deployment, a full authentication layer (e.g. OAuth2/JWT) and user-scoped database isolation must be added.
2. **Container Root vs User Namespace**: OpenFOAM container images often run internally as root. While `no-new-privileges` and `network_mode: none` provide strong containment, deploying Docker user namespace remapping (`userns-remap`) on the host provides an additional layer of defense.
3. **Data Retention**: STL files and generated meshes are retained in `workspace_jobs/`. For production deployments processing proprietary CAD models, configure periodic automated purging using the retention policy script.
